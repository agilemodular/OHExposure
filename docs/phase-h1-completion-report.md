## 3. What was done

| Area | Delivered | Evidence |
|---|---|---|
| Pilot gate register | 11 gates with owner, status, acceptance criteria, evidence, reviewer and date fields; decision log; **no gate accepted** | `pilot-gate-register.md` |
| Enforceable pilot controls | Assurance levels (demo, evaluation, pilot) settable only by a platform operator. In pilot organisations: conclusions require an approved method version, a professional-reference benchmark and a matching averaging period. Report issue requires a revision approved under those controls, and is refused if the method is later rejected. Method status, benchmark provenance and assurance level are frozen at approval. | `assurance.ts`; `test/assurance.test.ts` |
| No admin path to professional sign-off | Method reviews are written only through the owner connection, with a named reviewer, their competence, a past date and an evidence reference, and the person recording it cannot be the reviewer. The application role has no write right on method reviews or on tenant controls. | assurance and regression tests |
| Calculation capability matrix | Per-capability matrix: purpose, formula, inputs, units, averaging, missing data, non-detects, limitations, tests, review status and pilot-enabled. Screens and reports show "insufficient evidence — not calculated", "not reviewed" and provenance as distinct states. | `calculation-and-benchmark-specifications.md` |
| Professional validation pack | 19 conventions; 15 worked examples generated by the engine, with tolerances; restrictions; benchmark interpretation; example issued report; standard limitation statements; control-closure rules; findings register; sign-off. Software correctness and methodological suitability are kept separate. | `hygienist-review-pack.md`; `docs/examples/example-report.synthetic.html` |
| Reference data workflow | Controlled, all-or-nothing import that never edits existing versions. Professional rows must carry reviewer, date, source, permitted use and licence note, enforced by a database constraint. Three kinds of benchmark are kept visibly distinct. Pilot substances are not chosen by us. | `reference-data-workflow.md`; `scripts/import-reference-data.ts` |
| Offline data protection | Every persistence location reviewed. Online-only is the default. Offline storage is an encrypted per-user store with PIN lock, inactivity lock, purge after sync and reference expiry. Only worker reference codes go to devices. Recovery uses server-sealed, user-attested envelopes and a reviewer import page. The old plaintext store is migrated. Limitations are documented, not overstated. | `offline-field-capture.md`; browser check 20/20 (desktop) |
| Operational hardening | Session idle timeout. MFA now enforced on sessions that existed before MFA was required. HMAC-signed alert webhook. Readiness check of the latest migration. Production start guard for `FIELD_RECOVERY_KEK`. Backup and restore-verification scripts. Rollback runbook. Sign-out clears the cached page shell. | `operations.md` |
| Privacy | Draft PIA covering data flows, roles, categories, a per-class retention decision table (all *to be confirmed*), rights, risks, support access and incidents | `privacy-impact-assessment.md` (draft, not reviewed) |
| Field-device acceptance tests | 22 tests covering every required area. Separate result tables for physical-device runs and emulated runs; no physical device has been tested. | `field-device-test-script.md` |
| Pilot protocol and stop conditions | One organisation, one site; *To be confirmed* for unknowns; parallel running; full workflow; seven stop conditions with the suspension and resumption procedure. A control intervention or closure is never simulated. | `pilot-protocol.md` |
